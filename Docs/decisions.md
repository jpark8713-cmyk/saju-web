# 결정 기록

Claude Code가 갱신한다. 사업자 결정은 날짜와 함께 남기고, 아직 정해지지 않은 항목은 `TODO(owner)`로 둔다.

## D-001 지원 범위: 1900~2050년 (사업자 결정, 2026-10-20)

- 주 라이브러리 `@fullstackfamily/manseryeok` 1.0.8은 한국천문연구원 음양력 데이터를 1900~2050년만 담고 있다.
- SPEC 7장의 "2100년 직전" 경계 케이스는 "2050년 직전"으로 바꿔 테스트한다.
- 범위 밖 입력은 `CalendarInputError('outOfRange')`로 거부한다.
- 범위는 **입력한 달력의 연도** 기준이다. 양력 입력은 양력 1900-01-01~2050-12-31, 음력 입력은 음력 1900~2050년(변환한 양력도 범위 안이어야 함).
  그래서 양력 1900-01-01~1900-01-30은 받지만 그 날짜의 음력 표시는 1899년 12월로 나온다(예: 1900-01-01 → 음력 1899-12-01). 음력 1899년 입력은 받지 않는다.

## D-002 자시 처리: 야자시/조자시 구분 (사업자 결정, 2026-10-20)

- 설정 `jasiMode`: `split`(기본) | `unified`.
- `split`: 23시대(경도 보정 후 현지 시각)는 일주를 당일로 두고, 시주는 다음날 일간 기준 자시. 00시대는 다음날 일주.
  lunar-javascript `EightChar.setSect(2)`와 같다.
- `unified`(통자시): 23시부터 일주가 다음날로 넘어간다. `setSect(1)`과 같다.
- 시주는 두 방식이 같고 일주만 다르다.
- 참고: manseryeok `calculateSaju`는 23시대 시주를 **당일** 일간으로 계산해(예: 1988-02-15 23:30 → 丙子) 두 방식 어디에도 맞지 않는다. 엔진은 이 함수를 쓰지 않는다.

## D-003 시간 보정: 경도 보정 + 서머타임·과거 표준시 보정 (사업자 결정, 2026-10-20)

- 출생 순간: 입력한 벽시계 시각을 IANA tzdb `Asia/Seoul` 이력으로 UTC 순간으로 바꾼다(설정 `historicalTimezone`, 기본 켬).
  - tzdb에 1908년 이전 서울 지방평균시(+8:27:52), 1908~1911·1954~1961 UTC+8:30, 1948~1951·1955~1960·1987~1988 서머타임이 들어 있다.
  - Node 26.7.0 기준 ICU 78.3 / tzdb 2026c. 런타임 내장 데이터라 네트워크를 쓰지 않는다. Node를 올리면 tzdb가 바뀔 수 있으니 테스트를 다시 돌린다.
  - 서머타임 시작 때 없는 시각(예: 1987-05-10 02:30)은 전환 직전 오프셋(표준시)으로 해석하고 `nonexistentWallTime` 경고를 남긴다.
  - 서머타임 종료 때 두 번 있는 시각(예: 1987-10-11 02:30)은 앞의 순간(서머타임 쪽)을 택하고 `ambiguousWallTime` 경고를 남긴다.
- 현지 시각: 출생 순간(UTC) + 경도 × 4분 = 평균태양시(설정 `longitudeCorrection`, 기본 켬). 출생지를 비우면 동경 127°(서울).
  - 균시차(equation of time)는 **반영하지 않는다(사업자 결정, 2026-10-20).** 엄밀한 진태양시와는 최대 ±16분 정도 차이가 날 수 있다.
  - 일주·시주는 이 현지 시각으로, 년주·월주와 대운은 출생 순간으로 판정한다(절입은 절대 순간이므로 시간대와 무관).
- 경도 보정을 끄면 한국 표준시(UTC+9) 기준 시각을 쓴다. 서머타임 보정을 끄면 입력 시각을 UTC+9로 본다.

## D-004 년주·월주 경계: 분 단위 절입 순간으로 판정 (사업자 결정, 2026-10-20)

### 배경 (교차검증 결과)

1900-01-01~2050-12-31 전체 55,152일을 매일 12:00(KST)에 두 라이브러리로 비교했다(`tests/engine/sweep.test.ts`).

| 항목 | 결과 |
| --- | --- |
| 일주 | 55,151일 일치, 불일치 0 |
| 년·월주, 절입 당일 | 하루 단위 데이터라 비교 불가(절입 시각 전후가 다름) |
| 년·월주, 절입 전날·다음날 | 245일 불일치. manseryeok이 하루 일찍(또는 늦게) 월을 바꾼다. 예: 1900 소서는 07-08 00:10 KST인데 manseryeok은 07-07부터 癸未월 |

### 채택 기준

- **월지·년주 경계 = 절입 순간.** 절입 시각은 lunar-javascript 1.7.7의 천문 계산값(베이징 시간 UTC+8, 초 단위)에 8시간을 빼 UTC로 쓴다. 출생 순간이 절입 순간 이상이면 새 달이다.
- 월간은 년간 기준 오호둔법, 년주는 입춘 기준으로 **엔진 코드가** 계산한다(`src/engine/pillars.ts`).
- 일주는 율리우스 적일로 계산한다. 두 라이브러리 일진과 전 범위에서 일치함을 테스트로 고정했다.
- 음력 변환(윤달)은 manseryeok(한국천문연구원 기반)을 쓴다. lunar-javascript는 중국 음력(UTC+8 기준 합삭)이라 음력 날짜가 다른 날이 1900~2050 중 1,978일(59개 연도)이고, 그중에는 윤달 위치가 다른 해도 있다. 예: 2017년 한국 윤5월 / 중국 윤6월, 2012년 한국 윤3월 / 중국 윤4월.
- manseryeok의 1956-12-31 구멍은 전날 음력 + 1일로 메운다(`src/engine/calendar.ts`). 그 밖의 결함 날짜는 엔진이 manseryeok 월주를 쓰지 않으므로 결과에 영향이 없다.
- 테스트는 위 불일치 목록과 건수를 고정해 두어, 라이브러리를 올렸을 때 달라지면 실패한다.
- 절입 시각은 한국천문연구원 24절기 시각과 대조한다(`tests/engine/kasi.test.ts`, ±1분). fixture(`tests/fixtures/kasi-jie.json`)는 `npm run fetch:kasi`로 받는다(`.env`의 `DATAGOKR_API_KEY` 사용). 결과와 한계는 D-012.

## D-005 대운수: 년·개월까지 표시 (사업자 결정, 2026-10-20)

- 순행(양년생 남자·음년생 여자): 출생 → 다음 절입, 역행: 이전 절입 → 출생. 년간 음양은 입춘 기준 년주로 본다.
- 환산: 3일=1년, 1일=4개월, 1시간=5일. 분 단위로 계산하고 나머지는 버린다(4,320분=1년, 360분=1개월, 12분=1일).
- **초 단위 처리: 버림 유지(사업자 결정, 2026-10-20).** 설정 `daewoonRounding`(`floor` 기본 | `round`)으로 분리했다. `round`는 출생~절입 시간을 분으로 바꿀 때만 반올림하고, 그 뒤 년·개월·일 환산은 두 방식 모두 버림이다.
  - 예: 절입까지 359분 50초 → `floor` 359분 = 0년 0개월 29일, `round` 360분 = 0년 1개월 0일(`tests/engine/options.test.ts`).
- lunar-javascript `getYun(gender, 2)`와 환산 비율은 같지만 완전히 일치하지는 않는다. 1차 독립 리뷰(2026-10-20)에서 1900~2049년 47,614건을 비교한 결과, **년·개월이 1개월 다른 경우가 66건(0.14%)**, 일이 다른 경우가 1,882건이었다. 예: 절입까지 5시간 59분 53초 → 엔진 0년 0개월 29일, 라이브러리 0년 1개월 0일. 엔진은 초를 버리고 라이브러리는 다르게 처리하는 것으로 보이지만 원인은 분리하지 않았다(리뷰어 측정값이며 테스트로 고정하지는 않음). 경계 테스트 3건은 일치한다.
- 대운은 10개(100년)를 만든다(설정 `daewoonCount`, 1~12). 각 대운의 시작일은 출생 시각 + 대운수(년·개월·일·시) + 10년×순번이다(D-022에서 정밀화, 이전에는 출생 연·월 + 년·개월만 더해 한 달 일찍 나올 수 있었다).
- **대운 나이 표시: 세는 나이 + 연도 병기(사업자 결정, 2026-10-20).** `DaewoonEntry.koreanAge` = 대운 시작 연도 − 출생 연도 + 1. 근거 문구는 표준 표기 "K세(YYYY년 M월)부터 10년(나이는 세는 나이)"이다(D-022). 만 기준 경과(`startOffset`)와 시작일(`startYear/Month/Day`)도 데이터에 남긴다.

## D-006 시간 모름

- 시주는 null(3주)이고 오행은 6글자로 센다.
- 년·월주 판정과 대운 계산에는 12:00(설정 `unknownTimeAssumption`)을 쓴다.
- 그날(한국 벽시계 00:00~24:00) 안에 절입이 있으면 `unknownTimeOnJieDay` 경고를 남긴다(년·월주가 바뀔 수 있음).
- **플래그 + 안내 문구 데이터 제공(사업자 결정, 2026-10-20).** `SajuChart.notices`에 경고마다 `{ code, message }`를 넣고, `unknownTimeOnJieDay`에는 `jie: { name, localTime, ifBefore, ifAfter }`(절입 시각과 절입 전·후 출생일 때의 년·월주)를 함께 준다. 문구 기본안은 `src/engine/notices.ts`의 `NOTICE_MESSAGES`이며 바꿀 수 있다.
  - 문구에 "정오 출생으로 계산"이 들어 있으므로 `unknownTimeAssumption`을 바꾸면 문구도 같이 고친다.
- 서머타임 경고(`nonexistentWallTime`, `ambiguousWallTime`)에도 같은 방식으로 문구를 붙인다.

## D-010 근거(Evidence) 형식

- `{ id, kind, content, sourceFields, chartRefs, terms }`. SPEC 4장의 `종류/내용/근거 필드`를 `kind/content/sourceFields`로 옮겼다.
- `terms`는 그 근거에 등장하는 간지·십신 표기 목록이다. Phase 2에서 "근거 id의 내용과 문장의 간지·십신이 맞는지" 검사할 때 쓴다.
- `chartRefs` 형식: `year|month|day|hour.stem|branch`, `daewoon[n]`, `seun[n]`, `elements.wood|fire|earth|metal|water`.
  SPEC 예시(`일주.천간`, `대운[2]`)를 영어 키로 옮긴 것이다. `isValidChartRef(chart, ref)`로 유효성을 검사한다.
- id는 의미 기반이라 같은 입력이면 같은 id가 나온다(예: `pillar.day.stem`, `tenGod.month.branch`, `daewoon[2]`).
- 세운은 "올해·내년" 2개를 만든다. 엔진을 순수하게 유지하려고 기준 연도(`referenceYear`)를 인자로 받는다.

## D-012 절입 시각 검증: 천문연 대조 + 태양 황경 독립 계산 (사업자 결정, 2026-10-20)

### 천문연 API 대조 (2000~2028년)

- data.go.kr 15012690 `get24DivisionsInfo`는 **2000~2028년만** 응답한다(2026-10-20 확인, 그 밖의 연도는 HTTP 200에 빈 결과).
- 29개 연도 × 12절 = 348건 중 347건이 엔진 값과 ±1분 안에서 일치했다.
- 나머지 1건은 천문연 API 데이터 오류로 판정해 예외로 등록했다(`KNOWN_KASI_API_ERRORS`). 예외 행은 엔진과 **어긋나야** 통과하므로, 천문연이 값을 고치면 테스트가 실패해 알려 준다.
- 테스트가 조용히 약해지지 않게 한 장치(2차 독립 리뷰 지적 반영):
  - fixture가 없으면 건너뛰지 않고 **실패**한다. 12절 행 수를 348건(29년 × 12)으로 고정했다.
  - 같은 연도·절기 행이 2개 이상이면 실패한다.
  - 예외는 연도·이름에 더해 **천문연 시각이 오류 범위(2011-11-08 09:21~09:31) 안일 때만** 적용한다. 범위를 벗어난 행은 일반 행처럼 ±1분 검사를 받는다.
  - 예외 검사는 엔진 값이 독립 계산 범위(03:31:15 ±15분 = 03:16~03:46) 안인지도 확인한다.

| 2011년 입동 (황경 225°) | 시각 (KST) | 근거 |
| --- | --- | --- |
| 천문연 API | 2011-11-08 09:26 | `kst` 필드. 이 시각의 황경은 225.248°(아래 독립 계산) |
| 엔진 | 2011-11-08 03:34:56 | lunar-javascript 값을 UTC로 바꾼 것 |
| lunar-javascript 1.7.7 | 2011-11-08 02:34:56 (UTC+8) = 03:34:56 KST | `getJieQiTable()['立冬']` |
| 독립 계산 | 2011-11-08 03:31:15 | Meeus 저정밀식으로 황경 225°를 지나는 순간을 이분법으로 구함 |

- 검산 방법이 믿을 만한지 같은 달 다른 절기로 확인했다. 천문연 2011 상강 03:30 → 210.004°, 소설 01:08 → 240.005°로 기대값과 맞는다. 입동 행만 약 6시간(독립 계산 대비 354.7분) 어긋난다.
- 참고: 천문연 API의 2012년 입동(2012-11-07 09:26)도 시각이 09:26으로 같고, 그 행은 엔진과 ±1분 안에서 일치한다. 2011년 행에 2012년 시각이 잘못 들어간 것으로 보인다(추정, 천문연에 확인하지 않음).
- 엔진과 독립 계산의 3.7분 차이는 저정밀식 자체의 오차 범위(아래 참고) 안이다.

### 태양 황경 독립 계산 (천문연 대조가 없는 구간)

- 1900~1999년, 2029~2050년은 천문연 API 대조가 없다. 이 구간에서는 절입 시각을 lunar-javascript 천문 계산 하나에 기대므로 다른 경로로 검산한다.
- `tests/engine/sunLongitude.ts`: Meeus 『Astronomical Algorithms』 25장 저정밀 태양 겉보기 황경식(오차 약 0.01° ≈ 15분). ΔT(TT-UT)는 무시했다(이 범위에서 약 -3~+90초).
- `tests/engine/solarLongitude.test.ts`: 위 두 구간의 12절 모두에서 엔진 값과 lunar-javascript 절기표(엔진을 거치지 않고 직접 읽음)를 각각 독립 계산과 비교한다. 허용 오차는 ±15분이다.
- 측정 결과 (엔진 vs 독립 계산, 절댓값):

| 구간 | 건수 | 평균 | 최대 |
| --- | --- | --- | --- |
| 1900~1999 | 1,200 | 3.51분 | 11.61분 (1978 입하) |
| 2000~2028 (참고) | 348 | 3.63분 | 12.94분 (2013 입하) |
| 2029~2050 | 264 | 3.96분 | 12.63분 (2029 소서) |

- **한계:** 이 검산은 수 시간 단위의 큰 오류(예: 위 2011 입동 같은 오류, 시간대 환산 실수)는 잡지만, 분 단위 정확도는 보장하지 않는다. 오차 15분 안에서도 절입 순간 근처에 태어난 사람은 월주가 바뀔 수 있다. 천문연 대조가 있는 2000~2028년은 ±1분으로 확인했으므로, 같은 계산식을 쓰는 다른 연도도 비슷한 정확도일 것으로 보지만 직접 증명된 것은 아니다.
- 2000~2028년 평균 오차가 다른 구간과 비슷하다는 점(3.5~4.0분)은 이 오차가 대부분 저정밀식 쪽에서 생긴다는 근거다.

## D-014 총평 첫 문장: 코드 템플릿 (사업자 결정, 2026-10-20)

- 무료 미리보기의 총평 공개분(2문장, SPEC 기본값)은 AI 없이 코드 템플릿으로 만든다(`src/report/summaryTemplate.ts`). 무료 사용자에게 AI 비용이 들지 않는다.
- 결제 후 리포트의 총평도 **같은 템플릿 2문장으로 시작**하고, AI가 그 뒤 2문장을 이어 쓴다. 결제 전후로 같은 자리 문장이 바뀌지 않는다.
- 1문장: 일간 10종별 문장(근거 `dayMaster`).
- 2문장: 오행 분포 경우별 문장(근거 `elements.summary` + 해당 오행 `elements.*`).
  - 경우: 한 오행 과다(3개 이상) 5종, 한 오행 결핍 5종, 과다+결핍, 결핍 2개 이상, 과다 2개, 고름.
  - 과다·결핍 오행마다 행동 제안 문구가 다르다.
- 템플릿 문장도 AI 문장과 같은 검증(근거 id, 간지-근거 일치, 금지 표현, 120자)을 통과해야 한다. 1950~2040년을 13일 간격으로 훑은 표본(약 2,500건)으로, 일간 10종과 오행 경우 6가지가 모두 나오고 모두 통과함을 테스트한다(`tests/llm/template.test.ts`).

  - 대운 흐름: 현재·다음 대운 2개 × 3문장

- **모델 호출 설정:** `effort: medium`(Opus 5.5의 기본값, 명시), thinking은 기본(adaptive), `max_tokens` 16,000, 시스템 프롬프트는 캐시한다.

## D-017 풀이 검증 규칙과 재시도

- **문장마다 검사하는 항목(SPEC 1-0장, Phase 2):**
  - 근거 id가 1개 이상 있는가.
  - 모든 id가 이번 호출에 넘긴 근거 목록에 있는가.
  - 문장에 쓴 간지·십신이 넘긴 근거 전체에 있는가(근거 외 언급 금지). 그리고 그 문장이 **인용한** 근거에 있는가(내용 일치).
  - 금지 표현이 없는가.
  - 120자 이내인가. 문장 수가 맞는가.
- **간지·십신 표기 찾기(`src/llm/terms.ts`, 1차 리뷰 H1·M4, 2차 리뷰 HIGH-1·MEDIUM-1, 3차 리뷰 MEDIUM 반영):** 한글 간지는 일반 낱말(갑자기, 정해진, 기사, 임신…)과 겹친다. 그래서 다음 경우만 찾고, 한자를 뺀 모든 한글 규칙(십신 포함)은 **앞이 낱말 경계**여야 한다. "조사"에는 서술격 어미(입니다·이라서·이며·인·답게 등)도 포함한다.
  - 한자 천간·지지
  - 천간 + 제 오행을 **붙여 쓴** 낱말(갑목·병화·임수…). 뒤에 조사가 붙어도 찾는다. 낱말 중간("책임수행", "안정을 목표", "경금속")은 찾지 않는다.
  - 60갑자 이름 + 긴 접미어(일주·년주·월주·시주·대운·세운)
  - 60갑자 이름 + 짧은 접미어(년·월·일·시·운·생·해) + 경계(조사 또는 한글 아님). 그래서 "임신 시기", "경신 일정"은 간지로 보지 않는다.
  - 60갑자 이름 + 조사 0~2개 + 경계. 예: "갑자가", "정축이에요", "갑자 기운", "일주 정축", "정축, 을묘".
    - 일반 낱말과 겹치는 이름 18개(기사·신사·임신·임자·병자·기미·정사·정해·경신·정유·병신·신축·기축·무인·정미·을사·임진·경인)는 이 규칙에서 뺀다. 이 이름들은 한자나 접미어가 있을 때만 찾는다.
  - 십신·그룹 이름(칠살 = 편관). "고정관념"(정관)·"개인성향"(인성)처럼 낱말 중간은 찾지 않고, "상관없이", "상관 없이", "상관관계", "인성 교육", "인성이 좋다" 등은 뺀다.
  - 띄어 쓴 "정화 작업", "마음 정화 시간"은 천간으로 보지 않는다.
  - 리뷰가 찾은 놓침·오탐 문장(1차 20개, 2차 14개, 3차 13개)을 테스트로 고정했다(`tests/llm/validate.test.ts`).
  - **남은 한계:**
    - 위 18개 이름을 조사만 붙이거나 단독으로 한글로 쓰면(예: "임신이 들어와요", "기사 기운") 간지로 잡지 못한다.
    - 천간과 오행을 띄어 쓰면("갑 목") 잡지 못한다. 띄어 쓴 형태까지 잡으면 "책임 수행", "안정을 목표" 같은 흔한 문장이 거부되기 때문이다.
    - 한글 천간·지지 한 글자(갑·자)만 단독으로 쓴 경우도 잡지 못한다.
    - 프롬프트는 간지를 "갑자(甲子)"처럼 한자와 함께 쓰게 한다.
- 십신 그룹 근거(`tenGodGroup.*`)의 `terms`에는 그룹 이름과 **원국에 실제로 있는** 십신만 넣는다(1차 리뷰 M1). 0개인 그룹을 인용해 "정재가 있다"고 쓰면 거부된다.
- **금지 표현 1차 필터(`src/llm/forbidden.ts` + 주제별 `extraForbidden`, 1차 리뷰 H2, 2차 리뷰 MEDIUM-2·LOW 반영):** 정규식은 명백한 표현을 값싸게 거르는 1차 필터다. 표현 변형을 정규식만으로 다 막지는 못한다(3차 리뷰에서 세 라운드 연속 변형이 새로 나와 방식의 한계로 판단). 그래서 2차로 AI 검수를 둔다(D-020).
  - 질병·의료 판단: 몸·체력·신체 부위 + 약하다·나쁘다, 병이 나다, 다칠 수 있다, 건강 악화·건강에 유의, 병원·진단·수술 등
    - "수술하듯", "매출 신장"(낱말 경계)은 뺀다.
  - 투자 권유·재물 손실 단정: 금융상품, 주식을 사라는 말, 부동산·땅을 사라는 말, 빚·대출, 투자 권유, 수익 보장, 파산·손실·돈을 잃는다는 말
    - 앞에 비금융 대상(시간·노력·배움·관계·경험·사람 등)이 있는 "~에 투자"는 뺀다.
    - "주식 시장 분석 업무", "매수와 매도 타이밍"은 뺀다.
  - 사망·재앙 단정: 목숨·세상을 떠남·재난·화재·사고가 날 것이라는 말
    - "큰 사고 없이", "사고를 당하지 않게", "목숨 걸고", "화재 예방", "재난 대비"는 뺀다.
  - 불안을 키우는 단정: 반드시·절대 + 실패·망함·헤어짐 등, 이혼할 운·이혼 위험, 헤어질 수 있다
    - "절대로 망설이지 마세요"는 뺀다.
  - 입증할 수 없는 정확성 표현: 적중, 풀이의 정확도, 100% 맞음
    - "정확도 높은 일", "100% 몰입"은 뺀다.
  - 막아야 하는 문장 32개와 막지 않아야 하는 문장 21개를 테스트로 고정했다(`tests/llm/forbidden.test.ts`).
  - 정규식이 놓친 변형은 2차 AI 검수(D-020)가 맡는다.
- **문장 칸 하나 = 문장 하나(사업자 결정 2026-10-20):** 문장 끝 부호(. ! ? 。) 뒤에 공백과 글자가 이어지면 두 문장 이상으로 보고 거부한다(`multipleSentences`). 소수점처럼 부호 뒤에 공백이 없으면 문장 끝으로 보지 않는다. 프롬프트에도 같은 규칙을 넣었다. 1차 측정 결과에 이 규칙을 적용하면 Opus 1/114, Sonnet 5/114 칸이 걸린다(근거 id가 칸 단위라 문장 수가 어긋나면 근거 표시가 흐려진다). 정규식에서 자주 걸리는 오탐을 발견하면 테스트 문장에 추가해 고친다.
- **재시도:** 첫 시도 + 재시도 2회. 다음 경우 모두 재생성한다.
  - JSON 형식 오류, 검증 위반
  - 거절(`refusal`), 길이 초과(`max_tokens`)
  - 재시도 요청에는 위반 내용(최대 20개)을 덧붙인다.
  - 3회 모두 실패하면 `GenerationError`를 던진다. 주문 상태를 `failed`로 바꾸는 처리는 Phase 4다.
  - 한 작업(기본 또는 주제)이 실패하면 나머지 작업의 진행 중 요청과 남은 시도를 바로 취소한다(`AbortSignal`, 1차 리뷰 M2).
  - `GenerationError.attempts`에는 모든 작업의 시도 기록이 들어간다. 단, 취소된 진행 중 요청은 응답이 없어 사용량이 기록되지 않는다(실제로는 일부 과금될 수 있다).
  - 검증이 아닌 이유(API 오류, 호출 측 예산 제한)로 멈추면 `GenerationInterrupted`를 던진다. 원래 오류는 `cause`에, 그때까지의 시도 기록은 `attempts`에 담는다(2차 리뷰 MEDIUM-3). Phase 4에서 API 오류는 재시도·`failed` 처리의 근거로 쓴다.
- **거절 폴백(사업자 결정 2026-10-20: 켬):** `fallbacks: "default"`(beta `server-side-fallback-2026-07-01`)를 쓴다. 폴백 모델이 응답하면 모델별 사용량(`usage.iterations`)을 그 모델 단가로 계산한다.
- **테스트:** LLM은 가짜 구현(`tests/llm/fakes.ts`)으로 바꿔 끼워 테스트하며, 실제 호출 없이 CI를 통과한다.

## D-020 금지 표현 2차 필터: AI 검수 (사업자 결정, 2026-10-20)

- **배경:** 정규식 금지 사전은 독립 리뷰 3라운드 연속으로 놓친 변형이 새로 나왔다. 넓히면 정상 문장("갈등을 빚다", "적금에 돈을 넣다")이 걸렸다. 표현을 하나씩 막는 방식의 한계로 보고 사업자가 AI 검수를 결정했다.
- **흐름(`src/llm/generate.ts`, `src/llm/moderation.ts`):**
  1. 생성 → 형식·근거 id·간지·정규식 금지 표현 검증(1차).
  2. 1차를 통과한 시도의 AI 문장만 검수 모델(`claude-haiku-5-5`)에 넘겨 금지 범주를 판정한다(2차). 정규식에서 걸린 시도는 검수하지 않는다.
  3. 걸린 문장이 있으면 위치와 범주를 알려 주고 다시 생성한다(생성 재시도 한도 안에서, 첫 시도 + 2회).
  4. 총평 템플릿 문장은 코드가 쓴 고정 문장이라 검수하지 않는다(테스트로 검증, D-014).
- **범주:** `medical`(질병·의료 판단), `investment`(투자 권유·재물 손실 단정), `disaster`(사망·재앙 단정), `anxiety`(불안을 키우는 단정), `accuracy`(입증할 수 없는 정확성 표현). 프롬프트에 "해당하지 않는 예"(비유적 투자, 부정 표현, 일반 낱말)를 함께 준다.
- **검수 호출 실패 = 통과 아님(사업자 결정):**
  - API 오류, 거절(`refusal`), 길이 초과, 형식이 틀린 응답이면 검수 호출을 다시 시도한다(최대 3회).
  - 응답이 모든 문장 index를 정확히 한 번씩, 허용된 범주로만 담아야 유효하다.
  - 3회 모두 실패하면 문장을 통과시키지 않고 `GenerationError(reason: 'moderationUnavailable')`로 생성 실패 처리한다. 문장 문제가 아니므로 다시 생성하지는 않는다.
  - 테스트에서 "실패 시 통과"로 바꾸면 테스트가 실패함을 확인했다.
- **기록(사업자 결정):** 시도 기록(`AttemptRecord.moderation`)에는 걸린 문장 위치·범주, 검수 호출의 성공 여부·실패 이유 코드·사용량만 남긴다. 문장 원문과 사용자 입력은 남기지 않는다(테스트로 확인).
- **호출 설정:** Haiku 5.5, 노력도 `low`, `max_tokens` 4,000, 구조화 출력(JSON 스키마). Haiku에는 서버 측 거절 폴백이 없어 `fallbacks`를 보내지 않는다.
- **비용:** 리포트당 검수 호출은 기본 1회 + 주제당 1회다(재생성 시 추가). 단가는 Haiku 5.5 $0.10/$0.50(MTok)이며, 캐시 단가는 가격표에 없어 입력의 0.1배·1.25배로 가정했다(`src/llm/pricing.ts`). 실제 비용은 측정 스크립트가 `moderation.usd`로 따로 보고한다.

## D-022 대운 시작일과 숫자 표기 (사업자 지시, 2026-10-20)

- **문제:** 풀이에서 대운 시작을 "28세부터", "2026년 6월부터"처럼 다르게 썼다. 근거 문구에 나이, 연·월, "출생 후 n년 n개월"이 함께 있어 모델이 골라 썼다. 값 자체는 모두 근거에 있었다(20건 124개 숫자 중 근거에 없는 값 0개).
- **계산 정밀화:** 시작일 = 출생 벽시계 시각(입력한 양력 날짜·한국 시각, 시간 모름이면 12:00) + 대운수 년 → 개월 → 일 → 시(1분 = 2시간).
  - 말일은 맞춘다(2월 29일 + 1년 → 2월 28일).
  - 이전에는 출생 연·월에 년·개월만 더해 실제보다 한 달 일찍 나올 수 있었다.
  - `DaewoonEntry.startDay`를 추가했다.
  - lunar-javascript `getStartSolar()`와 대조했다(`tests/engine/daewoonStart.test.ts`). 테스트는 1902~2048년 표본 중 대운수(년·개월·일·시)가 라이브러리와 같은 출생만 비교하며, 비교 대상 2천여 건에서 100% 일치를 요구한다. 독립 리뷰가 따로 돌린 대조: 5일 간격 9,158건, 28~31일생(2월 29일·시간 모름 포함) 17,443건 모두 불일치 0.
  - 한국 시각 00시대 출생은 라이브러리 기준(베이징 시각, 한국 −1시간)으로 전날이라 일 단위로 달라질 수 있다. 리뷰 측정으로 00시대 13,848건 중 1,420건이 하루 차이였고 대부분 이 기준 차이다. 테스트는 00시대를 빼고 비교한다(엔진은 한국 벽시계 기준으로 일관되게 계산한다).
  - 대운수가 라이브러리와 다른 출생(초 단위 처리 차이, D-005)은 시작일도 다를 수 있다. 리뷰 측정: 31,618건 중 일 단위 1,293건(4.1%), 연·월 표기 33건(0.1%). 엔진의 정의(초 버림) 안에서는 일관된 값이다.
- **표준 표기:** 대운 시작은 `K세(YYYY년 M월)` 하나로 쓴다(세는 나이 + 시작 연·월, `daewoonStartLabel`). 대운 근거와 대운 방향 근거의 문구는 이 표기만 담고 "출생 후 n년 n개월"은 뺐다. 대운수 자체(년·개월)는 `SajuChart.daewoonStart`에 남아 화면에서 쓸 수 있다.
- **검증 규칙(`validateNumbers`):**
  - 숫자로 쓴 사실로 보는 표기: YYYY년 M월, YYYY.M, YYYY년, 두 자리 연도(뒤에 부터·에·에는·생·도가 올 때), M월, N세, N살, 한글 수사 + 살(여덟 살 등), n년 n개월. "10년간", "1~2문장", "30대", "3개"는 대상이 아니다.
  - 1) 문장 속 표준 표기 `K세(YYYY년 M월)`는 인용한 대운 근거의 표기와 **정확히** 같아야 한다(앞이 숫자가 아닌 경계로 찾는다. 전각 괄호는 반각으로 맞춘다). 다르면 `numberNotInEvidence`.
  - 2) 표준 표기를 지운 나머지 숫자 표기 중 인용한 세운의 연도("2026년")는 허용한다.
  - 3) 대운 근거(대운·대운 방향)를 인용한 문장에 그 밖의 나이·연·월이 남으면 거부한다(`daewoonStartFormat`). 표준 표기 옆에 다른 연도를 덧붙이는 것도 막는다(2차 리뷰 HIGH).
  - 4) 대운 근거를 인용하지 않은 문장은 남은 숫자 표기가 인용한 근거 문구에 있어야 한다(숫자 경계를 지켜 비교, `numberNotInEvidence`).
  - 리뷰가 찾은 우회·오탐·누락 사례를 테스트로 고정했다(`tests/llm/validate.test.ts`).
  - 두 자리 연도는 바로 뒤에 "부터"가 올 때만 사실로 본다(예: "98년부터"). "10년에 한 번", "20년에 걸쳐", "10년도 지나지 않아" 같은 기간 표현을 연도로 오인하던 오탐을 고쳤다(3차 리뷰 MEDIUM, 2026-10-20 사업자 지시).
  - **알려진 한계(3차 리뷰 LOW, 사업자 지시로 이번에는 고치지 않고 기록만 함):**
    1. 전각 숫자("２０１７년", "２８세(２０１７년 ８월)")는 `\d`에 걸리지 않아 대운 인용 문장에서도 통과한다(NFKC 정규화로 막을 수 있음).
    2. 구분자 날짜("2017/8부터", "2017-8부터")는 숫자 사실로 잡지 않는다.
    3. '살' 없는 한글 나이("이십팔 세부터", "서른 즈음")는 잡지 않는다.
    4. 연대 표현("70년대생")은 사실로도 오탐으로도 다루지 않는다(세운만 인용한 문장에서 통과).
    5. 두 자리 연도는 "부터"가 붙을 때만 잡으므로 "98년생", "98년에는", "98년도"는 대운 인용 문장에서도 통과한다(기간 표현 오탐을 없애기 위한 사업자 지시의 결과, 4차 리뷰 LOW).
    - 모두 모델이 쓸 가능성이 낮은 표기다. 프롬프트 규칙 8이 표준 표기를 요구한다. 실제 측정에서 나타나면 고친다.
  - 프롬프트 규칙 8번에 같은 내용을 넣었다.
- **영향 추정:** 이전 측정 결과 20건을 새 규칙으로 다시 검사하면, 위반이 있는 호출은 Opus 40개 중 12개, Sonnet 40개 중 11개다(모두 "28세부터"처럼 표준 표기가 아닌 대운 시작). 그때의 근거 문구가 여러 표기를 보여 줬기 때문이며, 새 문구와 프롬프트에서는 줄어들 것으로 봤다. **확인 결과(3차 측정):** 첫 시도 기준 Sonnet 2/40, Opus 0/40, 최종 결과 0건(D-024).
