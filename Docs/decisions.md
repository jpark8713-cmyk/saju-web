# 결정 기록

Claude Code가 갱신한다. 사업자 결정은 날짜와 함께 남기고, 아직 정해지지 않은 항목은 `TODO(owner)`로 둔다.

## D-001 지원 범위: 1900~2050년 (사업자 결정, 2026-10-20)

- 주 라이브러리 `@fullstackfamily/manseryeok` 1.0.8은 한국천문연구원 음양력 데이터를 1900~2050년만 담고 있다.
- SPEC 7장의 "2100년 직전" 경계 케이스는 "2050년 직전"으로 바꿔 테스트한다.
- 범위 밖 입력은 `CalendarInputError('outOfRange')`로 거부한다.
- 범위는 **입력한 달력의 연도** 기준이다. 양력 입력은 양력 1900-01-01~2050-12-31, 음력 입력은 음력 1900~2050년(변환한 양력도 범위 안이어야 함).
  그래서 양력 1900-01-01~1900-01-30은 받지만 그 날짜의 음력 표시는 1899년 12월로 나온다(예: 1900-01-01 → 음력 1899-12-01). 음력 1899년 입력은 받지 않는다.

## D-002 자시 처리: 야자시/조자시 구분 (사업자 결정, 2026-10-20)

- 설정 `jasiMode`: `split`(기본) | `unified`.
- `split`: 23시대(경도 보정 후 현지 시각)는 일주를 당일로 두고, 시주는 다음날 일간 기준 자시. 00시대는 다음날 일주.
  lunar-javascript `EightChar.setSect(2)`와 같다.
- `unified`(통자시): 23시부터 일주가 다음날로 넘어간다. `setSect(1)`과 같다.
- 시주는 두 방식이 같고 일주만 다르다.
- 참고: manseryeok `calculateSaju`는 23시대 시주를 **당일** 일간으로 계산해(예: 1988-02-15 23:30 → 丙子) 두 방식 어디에도 맞지 않는다. 엔진은 이 함수를 쓰지 않는다.

## D-003 시간 보정: 경도 보정 + 서머타임·과거 표준시 보정 (사업자 결정, 2026-10-20)

- 출생 순간: 입력한 벽시계 시각을 IANA tzdb `Asia/Seoul` 이력으로 UTC 순간으로 바꾼다(설정 `historicalTimezone`, 기본 켬).
  - tzdb에 1908년 이전 서울 지방평균시(+8:27:52), 1908~1911·1954~1961 UTC+8:30, 1948~1951·1955~1960·1987~1988 서머타임이 들어 있다.
  - Node 26.7.0 기준 ICU 78.3 / tzdb 2026c. 런타임 내장 데이터라 네트워크를 쓰지 않는다. Node를 올리면 tzdb가 바뀔 수 있으니 테스트를 다시 돌린다.
  - 서머타임 시작 때 없는 시각(예: 1987-05-10 02:30)은 전환 직전 오프셋(표준시)으로 해석하고 `nonexistentWallTime` 경고를 남긴다.
  - 서머타임 종료 때 두 번 있는 시각(예: 1987-10-11 02:30)은 앞의 순간(서머타임 쪽)을 택하고 `ambiguousWallTime` 경고를 남긴다.
- 현지 시각: 출생 순간(UTC) + 경도 × 4분 = 평균태양시(설정 `longitudeCorrection`, 기본 켬). 출생지를 비우면 동경 127°(서울).
  - 균시차(equation of time)는 **반영하지 않는다(사업자 결정, 2026-10-20).** 엄밀한 진태양시와는 최대 ±16분 정도 차이가 날 수 있다.
  - 일주·시주는 이 현지 시각으로, 년주·월주와 대운은 출생 순간으로 판정한다(절입은 절대 순간이므로 시간대와 무관).
- 경도 보정을 끄면 한국 표준시(UTC+9) 기준 시각을 쓴다. 서머타임 보정을 끄면 입력 시각을 UTC+9로 본다.

## D-004 년주·월주 경계: 분 단위 절입 순간으로 판정 (사업자 결정, 2026-10-20)

### 배경 (교차검증 결과)

1900-01-01~2050-12-31 전체 55,152일을 매일 12:00(KST)에 두 라이브러리로 비교했다(`tests/engine/sweep.test.ts`).

| 년·월주, 절입 전날·다음날 | 245일 불일치. manseryeok이 하루 일찍(또는 늦게) 월을 바꾼다. 예: 1900 소서는 07-08 00:10 KST인데 manseryeok은 07-07부터 癸未월 |

### 채택 기준

- **월지·년주 경계 = 절입 순간.** 절입 시각은 lunar-javascript 1.7.7의 천문 계산값(베이징 시간 UTC+8, 초 단위)에 8시간을 빼 UTC로 쓴다. 출생 순간이 절입 순간 이상이면 새 달이다.
- 월간은 년간 기준 오호둔법, 년주는 입춘 기준으로 **엔진 코드가** 계산한다(`src/engine/pillars.ts`).
- 일주는 율리우스 적일로 계산한다. 두 라이브러리 일진과 전 범위에서 일치함을 테스트로 고정했다.
- 음력 변환(윤달)은 manseryeok(한국천문연구원 기반)을 쓴다. lunar-javascript는 중국 음력(UTC+8 기준 합삭)이라 음력 날짜가 다른 날이 1900~2050 중 1,978일(59개 연도)이고, 그중에는 윤달 위치가 다른 해도 있다. 예: 2017년 한국 윤5월 / 중국 윤6월, 2012년 한국 윤3월 / 중국 윤4월.
- manseryeok의 1956-12-31 구멍은 전날 음력 + 1일로 메운다(`src/engine/calendar.ts`). 그 밖의 결함 날짜는 엔진이 manseryeok 월주를 쓰지 않으므로 결과에 영향이 없다.
- 테스트는 위 불일치 목록과 건수를 고정해 두어, 라이브러리를 올렸을 때 달라지면 실패한다.
- 절입 시각은 한국천문연구원 24절기 시각과 대조한다(`tests/engine/kasi.test.ts`, ±1분). fixture(`tests/fixtures/kasi-jie.json`)는 `npm run fetch:kasi`로 받는다(`.env`의 `DATAGOKR_API_KEY` 사용). 결과와 한계는 D-012.

## D-005 대운수: 년·개월까지 표시 (사업자 결정, 2026-10-20)

- 순행(양년생 남자·음년생 여자): 출생 → 다음 절입, 역행: 이전 절입 → 출생. 년간 음양은 입춘 기준 년주로 본다.
- 환산: 3일=1년, 1일=4개월, 1시간=5일. 분 단위로 계산하고 나머지는 버린다(4,320분=1년, 360분=1개월, 12분=1일).
- **초 단위 처리: 버림 유지(사업자 결정, 2026-10-20).** 설정 `daewoonRounding`(`floor` 기본 | `round`)으로 분리했다. `round`는 출생~절입 시간을 분으로 바꿀 때만 반올림하고, 그 뒤 년·개월·일 환산은 두 방식 모두 버림이다.
  - 예: 절입까지 359분 50초 → `floor` 359분 = 0년 0개월 29일, `round` 360분 = 0년 1개월 0일(`tests/engine/options.test.ts`).
- lunar-javascript `getYun(gender, 2)`와 환산 비율은 같지만 완전히 일치하지는 않는다. 1차 독립 리뷰(2026-10-20)에서 1900~2049년 47,614건을 비교한 결과, **년·개월이 1개월 다른 경우가 66건(0.14%)**, 일이 다른 경우가 1,882건이었다. 예: 절입까지 5시간 59분 53초 → 엔진 0년 0개월 29일, 라이브러리 0년 1개월 0일. 엔진은 초를 버리고 라이브러리는 다르게 처리하는 것으로 보이지만 원인은 분리하지 않았다(리뷰어 측정값이며 테스트로 고정하지는 않음). 경계 테스트 3건은 일치한다.
- 대운은 10개(100년)를 만든다(설정 `daewoonCount`, 1~12). 각 대운의 시작 시점은 출생 연·월 + 대운수 + 10년×순번.
- **대운 나이 표시: 세는 나이 + 연도 병기(사업자 결정, 2026-10-20).** `DaewoonEntry.koreanAge` = 대운 시작 연도 − 출생 연도 + 1. 근거 문구는 "N세(세는 나이, YYYY년 M월)부터 10년"이다. 만 기준 경과(`startOffset`)도 데이터에 남긴다.

## D-006 시간 모름

- 시주는 null(3주)이고 오행은 6글자로 센다.
- 년·월주 판정과 대운 계산에는 12:00(설정 `unknownTimeAssumption`)을 쓴다.
- 그날(한국 벽시계 00:00~24:00) 안에 절입이 있으면 `unknownTimeOnJieDay` 경고를 남긴다(년·월주가 바뀔 수 있음).
- **플래그 + 안내 문구 데이터 제공(사업자 결정, 2026-10-20).** `SajuChart.notices`에 경고마다 `{ code, message }`를 넣고, `unknownTimeOnJieDay`에는 `jie: { name, localTime, ifBefore, ifAfter }`(절입 시각과 절입 전·후 출생일 때의 년·월주)를 함께 준다. 문구 기본안은 `src/engine/notices.ts`의 `NOTICE_MESSAGES`이며 바꿀 수 있다.
  - 문구에 "정오 출생으로 계산"이 들어 있으므로 `unknownTimeAssumption`을 바꾸면 문구도 같이 고친다.
- 서머타임 경고(`nonexistentWallTime`, `ambiguousWallTime`)에도 같은 방식으로 문구를 붙인다.

## D-010 근거(Evidence) 형식

- `{ id, kind, content, sourceFields, chartRefs, terms }`. SPEC 4장의 `종류/내용/근거 필드`를 `kind/content/sourceFields`로 옮겼다.
- `terms`는 그 근거에 등장하는 간지·십신 표기 목록이다. Phase 2에서 "근거 id의 내용과 문장의 간지·십신이 맞는지" 검사할 때 쓴다.
- `chartRefs` 형식: `year|month|day|hour.stem|branch`, `daewoon[n]`, `seun[n]`, `elements.wood|fire|earth|metal|water`.
  SPEC 예시(`일주.천간`, `대운[2]`)를 영어 키로 옮긴 것이다. `isValidChartRef(chart, ref)`로 유효성을 검사한다.
- id는 의미 기반이라 같은 입력이면 같은 id가 나온다(예: `pillar.day.stem`, `tenGod.month.branch`, `daewoon[2]`).
- 세운은 "올해·내년" 2개를 만든다. 엔진을 순수하게 유지하려고 기준 연도(`referenceYear`)를 인자로 받는다.

## D-012 절입 시각 검증: 천문연 대조 + 태양 황경 독립 계산 (사업자 결정, 2026-10-20)

### 천문연 API 대조 (2000~2028년)

- data.go.kr 15012690 `get24DivisionsInfo`는 **2000~2028년만** 응답한다(2026-10-20 확인, 그 밖의 연도는 HTTP 200에 빈 결과).
- 29개 연도 × 12절 = 348건 중 347건이 엔진 값과 ±1분 안에서 일치했다.
- 나머지 1건은 천문연 API 데이터 오류로 판정해 예외로 등록했다(`KNOWN_KASI_API_ERRORS`). 예외 행은 엔진과 **어긋나야** 통과하므로, 천문연이 값을 고치면 테스트가 실패해 알려 준다.
- 테스트가 조용히 약해지지 않게 한 장치(2차 독립 리뷰 지적 반영):
  - fixture가 없으면 건너뛰지 않고 **실패**한다. 12절 행 수를 348건(29년 × 12)으로 고정했다.
  - 같은 연도·절기 행이 2개 이상이면 실패한다.
  - 예외는 연도·이름에 더해 **천문연 시각이 오류 범위(2011-11-08 09:21~09:31) 안일 때만** 적용한다. 범위를 벗어난 행은 일반 행처럼 ±1분 검사를 받는다.
  - 예외 검사는 엔진 값이 독립 계산 범위(03:31:15 ±15분 = 03:16~03:46) 안인지도 확인한다.

| 2011년 입동 (황경 225°) | 시각 (KST) | 근거 |
| --- | --- | --- |
| 천문연 API | 2011-11-08 09:26 | `kst` 필드. 이 시각의 황경은 225.248°(아래 독립 계산) |
| 엔진 | 2011-11-08 03:34:56 | lunar-javascript 값을 UTC로 바꾼 것 |
| lunar-javascript 1.7.7 | 2011-11-08 02:34:56 (UTC+8) = 03:34:56 KST | `getJieQiTable()['立冬']` |
| 독립 계산 | 2011-11-08 03:31:15 | Meeus 저정밀식으로 황경 225°를 지나는 순간을 이분법으로 구함 |

- 검산 방법이 믿을 만한지 같은 달 다른 절기로 확인했다. 천문연 2011 상강 03:30 → 210.004°, 소설 01:08 → 240.005°로 기대값과 맞는다. 입동 행만 약 6시간(독립 계산 대비 354.7분) 어긋난다.
- 참고: 천문연 API의 2012년 입동(2012-11-07 09:26)도 시각이 09:26으로 같고, 그 행은 엔진과 ±1분 안에서 일치한다. 2011년 행에 2012년 시각이 잘못 들어간 것으로 보인다(추정, 천문연에 확인하지 않음).
- 엔진과 독립 계산의 3.7분 차이는 저정밀식 자체의 오차 범위(아래 참고) 안이다.

### 태양 황경 독립 계산 (천문연 대조가 없는 구간)

- 1900~1999년, 2029~2050년은 천문연 API 대조가 없다. 이 구간에서는 절입 시각을 lunar-javascript 천문 계산 하나에 기대므로 다른 경로로 검산한다.
- `tests/engine/sunLongitude.ts`: Meeus 『Astronomical Algorithms』 25장 저정밀 태양 겉보기 황경식(오차 약 0.01° ≈ 15분). ΔT(TT-UT)는 무시했다(이 범위에서 약 -3~+90초).
- `tests/engine/solarLongitude.test.ts`: 위 두 구간의 12절 모두에서 엔진 값과 lunar-javascript 절기표(엔진을 거치지 않고 직접 읽음)를 각각 독립 계산과 비교한다. 허용 오차는 ±15분이다.
- 측정 결과 (엔진 vs 독립 계산, 절댓값):

| 구간 | 건수 | 평균 | 최대 |
| --- | --- | --- | --- |
| 1900~1999 | 1,200 | 3.51분 | 11.61분 (1978 입하) |
| 2000~2028 (참고) | 348 | 3.63분 | 12.94분 (2013 입하) |
| 2029~2050 | 264 | 3.96분 | 12.63분 (2029 소서) |

- **한계:** 이 검산은 수 시간 단위의 큰 오류(예: 위 2011 입동 같은 오류, 시간대 환산 실수)는 잡지만, 분 단위 정확도는 보장하지 않는다. 오차 15분 안에서도 절입 순간 근처에 태어난 사람은 월주가 바뀔 수 있다. 천문연 대조가 있는 2000~2028년은 ±1분으로 확인했으므로, 같은 계산식을 쓰는 다른 연도도 비슷한 정확도일 것으로 보지만 직접 증명된 것은 아니다.
- 2000~2028년 평균 오차가 다른 구간과 비슷하다는 점(3.5~4.0분)은 이 오차가 대부분 저정밀식 쪽에서 생긴다는 근거다.

## D-013 계산 설정 검증

- `buildChart`는 설정을 합친 뒤 `validateSettings`로 검사하고, 틀리면 일반 `Error`를 던진다(사용자 입력이 아니라 코드 설정 실수이므로 `CalendarInputError`와 구분).
- 검사 항목: `jasiMode`, `longitudeCorrection`·`historicalTimezone`(boolean), `defaultLongitude`(동경 120~135°, 입력 경도와 같은 범위), `unknownTimeAssumption`(0~23시, 0~59분 정수), `daewoonCount`(1~12 정수), `daewoonRounding`(`floor`|`round`).
- `daewoonCount`가 1 이상이므로 근거 `daewoon.direction`의 `chartRefs`는 비지 않는다.
